# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Two things that must not be confused:

- **The spec** — `docs/BUILD-PLAN.md` ("Video Imposter — Build Plan", 21 sections). This is the **authoritative target**. Its Section 20 is a confirmed-decisions log; treat those values as binding, not suggestions.
- **The code in `src/`** — an early, partial sketch of the functional plumbing. Per spec Section 21, it is **missing most of the spec** and its **visual design should be ignored entirely**. Do not treat the current feature set as the goal.

**The visual target is `vhs-frontend-example/`**, not `src/`. Spec §21 is explicit: where `vhs-frontend-example` and the general style direction in §18 conflict on a visual detail, `vhs-frontend-example` wins. The current Tailwind theme and `src/app/globals.css` component classes are *not* the design to build toward.

When a request is ambiguous, the spec decides. When the spec and the code disagree, the code is what's wrong — see the divergence table below.

## Commands

```bash
npm install
npx prisma generate && npx prisma db push   # required before first run, and after any schema change
npm run dev                                 # tsx server.js — Next.js + Socket.io on :3000
npm run build                               # next build
npm run lint                                # next lint
node vhs-frontend-example/server.js         # visual reference, static, :9000
```

- **Never start the app with `next dev`.** Socket.io is attached to a custom HTTP server in `server.js`; the plain Next dev server has no websocket layer and every room/game feature silently breaks.
- `npm start` is written as `NODE_ENV=production tsx server.js` (POSIX syntax). On this Windows machine that fails in PowerShell — use the Bash tool, or `$env:NODE_ENV='production'; npx tsx server.js`.
- No test framework is configured. Verification is `npx tsc --noEmit`, `npm run lint`, and `npx next build`.
- **For a quick manual check, host a lobby and press SIMULATE PLAYERS** (dev only — see the bots section below). It fills the room with bots that watch, react, speak and vote, so a whole round is playable solo in one browser.
- **For anything you need to assert on, script socket clients** instead, not four browser windows. Boot the server, then drive `socket.io-client` through a full round (create → join ×3 → start → syncReady → videoEnded → readyToAdvance → word ×N → vote → results) asserting on the payloads. A round takes seconds and catches phase-machine regressions that manual play misses. Run such a script from a scratch directory with its own `npm install socket.io-client` — `NODE_PATH=<repo>/node_modules` works for CommonJS `require` but **not** for ESM `import`, which ignores it and fails with `ERR_MODULE_NOT_FOUND`.

## Current architecture

Next.js 14 App Router frontend + a Socket.io game server in the same process. `server.js` (CommonJS) boots Next, creates the socket.io `Server`, and calls `registerSocketHandlers(io)` from `src/server/socketHandlers.ts` — `tsx` is what lets a `.js` entrypoint `require` that TS module.

Note the stack already diverges from spec §15, which recommended React+Vite / Supabase / LiveKit. The existing Next.js + Prisma + custom-socket-server choice is what's actually built; don't rewrite it wholesale without asking.

**Two separate stores, deliberately:**
- **Game state is in-memory only** — a `Map<code, RoomState>` in `src/server/gameState.ts`. Restarting the dev server destroys every active room, and rooms still can't be shared across instances. Player identity, though, is no longer the socket — see the reconnect section below.
- **Prisma/SQLite holds only durable, non-game data** — users, NextAuth accounts/sessions, video presets. The `GameHistory` model exists in the schema but nothing reads or writes it.

**The core secrecy invariant.** The game rests on players not knowing their role. `sanitizeRoom()` in `socketHandlers.ts` strips `normalVideoUrl`/`imposterVideoUrl` from every room broadcast, exposing only `hasNormalVideo`/`hasImposterVideo` booleans. URLs reach clients only through the per-socket `game:assigned` emit. Any new broadcast, event payload, or API response touching room settings must preserve this — leaking a URL breaks the game silently, not loudly.

Roles are covered by the same rule: `game:assigned` carries **only** `videoUrl`. `GameAssignment` deliberately has no `isImposter` field — a client that knows its role can read it from devtools, which defeats the mechanic. Roles first appear in the `game:results` payload, after voting closes. Don't add a role flag to any earlier payload.

**Phase machine** — `lobby → playing → words → deliberation → results`, and back to `lobby` only when somebody clicks Rejoin (see below). Names match the spec's vocabulary (sections 6–8). The server owns `room.phase`; `src/hooks/useRoom.ts` mirrors it into React state, and `src/app/room/[code]/page.tsx` switches between `LobbyScreen` / `GameScreen` / `WordsScreen` / `DeliberationScreen` / `ResultsScreen`. Transitions:
- `playing → words`: **Ready Check** (section 6). Every player reports their own `game:videoEnded`, and clicks Ready (`game:readyToAdvance`). Advances when all are ready, or 10s after the *imposter's* video ends — the server starts that grace timer because it alone knows who the imposter is. **Ready is deliberately not gated on your own video having finished**, which §6 implies it would be: it is live for the whole `playing` phase, so a lobby that has all seen enough cuts a long clip short. That's a product decision, not an oversight — don't "restore" the gate. One impatient player skips nothing; `allReadyToAdvance` still needs every connected player.
- `words → deliberation`: when the turn order is exhausted. Each turn is 10s; timing out auto-skips with a blank word.
- `deliberation → results`: when every *active* player has voted, or the 90s window expires — whichever comes first.
- `deliberation → words` **again**, in a 2-imposter game only — see below.
- A **tie** does not resolve to results. `resolveVote()` returns a `revote`, and the round loops (see below).

**The 2-imposter game runs the loop twice (section 3).** `imposterCount` is a host setting that unlocks at 7 players; at 2, `totalGameRounds()` returns 2 and the machine becomes `words → deliberation → words → deliberation → results`. `room.gameRound` tracks which pass you're in and `room.accusedIds` collects who has been ejected. **The accused's role is not revealed between rounds** — that withheld reveal is the whole mechanic, so `accusedIds` is safe to broadcast but nothing role-shaped may ride along with it. `activePlayers()` (connected *and* not accused) is what drives turn order, the ballot, and the "everyone voted" check; `connectedPlayers()` still covers the Ready Check, which happens once before round 1. Round 2 re-enters through `beginNextGameRound()` → `emitWordPhaseStart()`, skipping `beginWordPhase`'s caller because the turn order is already set. There is no second video and no second Ready Check.

Two 2-imposter rules cut across the normal ones. `resolveVote()` gains an `allImpostersCaught` outcome: a deadlock with no swing voters *between exactly the imposters* resolves for the crew instead of looping, because the group collectively named precisely the right people. And rewards stop being a win/lose flip — `coinsFor()` pays off the section 3 table by how many of the two were caught (crew 50/100/150, suspects 150/75/50), which is why `GameResults` carries `outcome: 'crew' | 'imposter' | 'split'` rather than just `crewWins`.

**Timers are server-authoritative.** One `setInterval` per room in the module-level `roomTimers` Map, driven through `setRoomTimer()`/`clearRoomTimer()`. Phases are sequential so a single slot suffices. **Every path that ends a phase must clear it** — disconnects, `game:rejoin`, room deletion — or intervals tick against a dead room. Each tick re-reads the room via `getRoom()` and bails if the phase moved on, so a stale timer cannot corrupt a later phase. The reconnect grace timers are a *separate* map (`dropTimers`, keyed `code:playerId`) because several players can be inside their window at once, which the one-slot-per-room rule can't express.

**A player is a browser, not a socket.** `Player.id` is the durable `imposter_player_id` from `src/lib/playerId.ts` — minted into localStorage on first use, sent on `room:create`/`room:join` — and `Player.socketId` is the current transport. Everything that names a player by id (`votes`, `turnOrder`, `imposterIds`, `accusedIds`, `wordsUsed`, `readyToAdvance`) therefore survives a reconnect untouched; only `socketId` changes. **Anything emitting to one player must use `player.socketId`, not `player.id`** — `io.to(player.id)` now addresses nothing and fails silently, which is exactly how a role assignment goes missing. Handlers get the actor from `socket.data.playerId` via `actorId(socket)`, never from `socket.id`; `findRoomBySocket()` is the one place that still looks a socket up, for the disconnect path. Client-side, "me" is `getPlayerId()` — the components' prop is `playerId` and comparing against `socket.id` is now wrong everywhere.

**Every `room:join`/`room:create` emit must carry `playerId`, and one socket may hold only one player row.** These are the same rule from the two ends. `durableId()` falls back to `socket.id` when the field is missing, so an emit that forgets it mints a player keyed on a value that changes on the next reconnect — and if that socket then joins *again* with the real localStorage id, the room ends up holding **two rows for one person**. Only one of them can ever act, because handlers resolve the actor through `socket.data.playerId`; the other sits there `connected`, never ready, never voting, and every gate that waits on all players waits forever. This shipped: `/dashboard`'s `joinByCode` omitted the field while `hostRoom` sent it, so joining a public lobby (never hosting one) produced a lobby that showed three players and counted two, and the videos never started. Symptom to recognise: a head count that disagrees with the roster.

`dropStaleSocketRows()` in `gameState.ts` now enforces the invariant server-side, ahead of all three `room:join` branches *and* ahead of the phase/full guards — a phantom must never be what makes a room look full. It drops the stale row rather than re-keying it: re-keying would have to rewrite every id-keyed structure on `RoomState` (`votes`, `turnOrder`, `imposterIds`, `accusedIds`, `readyToAdvance`, `wordsUsed`…) and a partial rewrite is a silent corruption, while the caller seats the replacement immediately after. Both the fallback and the cleanup `console.warn` — the bug's whole cost was being silent.

**Dropping is not leaving.** A lost socket marks the player `disconnected` and arms a `DISCONNECT_GRACE_SECONDS` (60s) timer; they keep their seat, their vote, their turn slot, their role and — deliberately — the host seat, since a host refreshing is the commonest reconnect there is. `activePlayers()` already excluded them, so no phase waits on them: the Ready Check, the ballot and "everyone has voted" all shrink to who is actually present, and `advanceTurn()` skips over an absent player's slot rather than burning their 10s. Only when the grace expires does `finalizeDrop()` run, which is the old disconnect behaviour verbatim (remove, transfer host, splice the turn order, reap the room). Coming back is just `room:join` again: same `playerId` means reattach, and `sendCatchUp()` replays the current phase to that one socket using the same events the live broadcasts use — including `game:wordHistory` (the board, since `game:wordPhaseStart` clears it) and `room.lastResults` (the reveal, verbatim). `room.playAt` lets a player who reconnects mid-video be played straight back in instead of the room waiting on them a second time.

Two consequences worth keeping in mind. `room.words` and `room.lastResults` exist **only** so a reconnect has something to come back to — nothing else reads them. And chat history is deliberately *not* kept: the words are evidence, chat is chatter, and buffering it is a moderation surface nobody has asked for yet.

**Leaving on purpose is `room:leave`, and it has to be sent explicitly.** `getSocket()` is a singleton that survives client-side navigation, so routing away from `/room/[code]` disconnects nothing — without this event a lobby you walked out of goes on holding you, and itself, open until you close the tab. Both LEAVE buttons (`LobbyScreen`, `ResultsScreen`) emit it before `router.push`. **Where they push is `useHomeHref()` (`src/lib/useHomeHref.ts`), never a bare `/dashboard`** — that route's gate keys on `?guest=1` alone, so a literal `/dashboard` pushed a guest straight back to the landing page, which is what LEAVE actually did. The hook resolves signed-in → `/dashboard`, saved guest identity → `/dashboard?guest=1`, neither → `/`, and the header logo in `CrtShell` reads the same one, so the two exits cannot drift apart. The handler `cancelDrop`s first, because leaving is the opposite of dropping: no grace window, the seat goes now, and `finalizeDrop()` reaps the room if that was the last player. It is deliberately **not** wired to page unmount — React Strict Mode double-invokes effect cleanups in dev, which would eject a player from a lobby they are still sitting in.

**One open lobby per host.** `findRoomHostedBy()` (`gameState.ts`) is checked on `room:create`; if you already host one, `closeRoom()` shuts it under whoever is in it and the new lobby is created anyway. Superseding rather than refusing is the point — refusing would strand you behind a lobby you thought you had left. Three details: the rule keys on who is **currently** host, not on who created the room, so a host transfer frees you to open another and there is no creator field to keep in step; a signed-in host matches on `userId` and a guest on their durable browser `playerId`, so guest mode isn't an unlimited lobby-spawner; and `closeRoom()` reuses `room:kicked` rather than adding an event, because the client already maps that to `isKicked` and routes those players to `/dashboard`, which is exactly where a closed lobby should leave them. `socket.data.userId` is filled in by an async verify, so a create that beats it falls through to the player-id branch — that can only scope the rule more narrowly, never to the wrong account.

**Results ends the lobby; `game:rejoin` re-forms it.** There is deliberately no host-only "replay everyone" button — a finished round puts every player out, and each one opts back in for themselves. The first Rejoin runs `reformLobby()`: the room drops back to `lobby` with its settings and `usedVideoIds` intact, the clicker becomes host (the old one may never come back), and everyone else moves to `room.pastPlayers` and is taken out of the socket.io room so a lobby they haven't opted into stops updating the results screen under them. Later Rejoins restore identity from `pastPlayers` rather than trusting the client to say who it is, and re-`join` the channel. Rejoining twice is a no-op, and a room that emptied out answers with an error instead of resurrecting itself.

**Custom is a switch on a mode, not a mode.** It used to be a sixth video card, which made the obvious request unsayable: *I want to play Questions, with my own pair.* `settings.useCustomContent` is now a toggle that applies to whatever mode the lobby has picked, and `CustomContentPanel` renders it at the bottom of the GAME MODE tab — after the grid, because it modifies the choice made above it.

**`supportsCustomContent()` is the gate, and it names two styles.** A host can type a *pair*: two links for a video mode, two cards for Words or Questions. Fake Artist, Wavelength and Bluff each need something structurally different (a word plus a category, a labelled scale plus a hidden point, a word plus its real dictionary definition), so the panel tells that lobby the mode does not take one rather than showing a form that cannot work. `usesCustomContent(room)` in `gameState.ts` is the server-side pairing of switch-and-gate, and it is the **single** answer four places need to agree on: the start check, the bot-fill default, the deal, and the spectator assignment. The switch alone is not enough — it stays on when the host flips to Fake Artist, and a mode with nothing to type must not leave a player sitting out for content nobody used.

**The custom pair is under the same secrecy invariant as the URLs.** `settings.customNormalPrompt` / `customImposterPrompt` are server-only; `sanitizeRoom()` carries `hasNormalPrompt` / `hasImposterPrompt` and never the text, and `assignmentFor()` stays the one place either half leaves the server. `CUSTOM_CATEGORY` still exists but nothing produces it — `room:updateSettings` translates an incoming `'custom'` into "switch on" so a stale client tab lands somewhere real instead of on a mode that no longer exists.

**Whoever supplies the content sits the round out (section 4).** They wrote both halves, so they already know which is which — the rule is unchanged, it just now covers a typed pair as well as two pasted links. `room.customContentAuthorId` records whoever last set either, tracked rather than assumed to be the host, because the host can be handed on afterwards and it is the person who saw the content who knows. At `game:start` `assignSpectator()` flags them, and from there `activePlayers()` excludes them exactly like the round-1 accused: no card, no place in the turn order, no vote, no imposter draw, and a zero reward (paying participation coins would let a host farm them without playing). The flag is per-round and cleared on the next start, so it follows the content rather than the person.

Two knock-ons. A custom lobby needs **5** people to field a 4-player game, and the start check counts non-spectators; the lobby says who is sitting out before anyone hits start rather than springing it when the tape rolls. And turning the switch **off** clears both halves and the author — keeping them would let a second press restore a pair the lobby has been told is gone, and quietly make that player a spectator again.

**Voting visibility is a host setting, and enforcing it is three separate places (§4, §8).** `settings.voteVisibility` is `'public' | 'anonymous'`, defaults to public, and — like every other setting — is lobby-phase only, because flipping it mid-ballot would retroactively publish votes cast in confidence. Public means §4's "everyone sees live who's voting for whom", which the screen genuinely didn't do before. Anonymous withholds all of it until the final tally at results, and "only the final tally" is literal: individual ballots are never published, not even once the round is over. The three leaks, all closed via `isAnonymousVote()`:

1. `sanitizeRoom().votes` — the voter→target map, blanked when anonymous.
2. `vote:tally` — built by `tallyPayload()`; `tally` and `ballots` go null. The two progress numbers still go out, because "3 of 5 have voted" reveals nothing about targets and the phase is unreadable without it.
3. `game:revote` — the subtle one. Being on `eligibleVoters` means you backed *neither* tied candidate, so the roster is itself a statement about your ballot. `announceRevote()` broadcasts room-wide when public, but emits **per socket** when anonymous, with `eligibleVoters: null` and a `canRecast` boolean that speaks only about the recipient. Client-side, prefer `canRecast` over `eligibleVoters.includes(me)`.

`sendCatchUp()` repeats all three rules — a reconnect must not be a way around them.

**The live ballot rides on `vote:tally`, not on `room.votes`.** Casting a vote does not emit `room:updated`, so a screen reading `room.votes` shows a ballot frozen at the moment deliberation opened. `VoteTally.ballots` is the live channel; `RoomPublic.votes` is only a snapshot.

**Tie-breaking (section 8)** lives in `resolveVote()` / `beginRevote()` in `gameState.ts`. On a tie, voters who backed *neither* tied candidate are the swing voters: only their ballots are cleared, and they recast restricted to the tied pair. Voters already behind a tied candidate keep their vote. If there are no swing voters at all, the whole ballot re-runs among the tied players and loops until somebody switches — the round cannot conclude on a tie. `revoteCandidates` being non-null is what marks a restricted ballot.

**One deadlock is unbreakable and must not loop.** When the only two players still in the game are the two tied candidates, neither can switch without voting for themselves, so every re-vote reproduces the same 1–1 and the room would re-arm its deliberation timer forever. `resolveVote()` ends that case with `accusedId: null` — no accusation, the group failed to agree. Larger deadlocks are still left to loop, because with three or more voters somebody can always move. Reachable whenever a lobby shrinks to two active players, which since reconnect landed includes two people simply losing signal.

**Adding a socket event requires edits in three places**, and doing two of three fails silently:
1. `src/server/socketHandlers.ts` — the handler, plus any `gameState.ts` mutator it needs.
2. `src/hooks/useRoom.ts` — a listener in the `useEffect`, *and* the matching `socket.off` in the cleanup.
3. `src/hooks/useRoom.ts` — a `useCallback` in the `actions` object, which is what components call.

**Type duplication is intentional.** `src/server/gameState.ts` holds the full server-side `RoomState` (URLs, imposter IDs, votes); `src/types/index.ts` holds the sanitized `RoomPublic` the client sees. Changing a room field means touching both plus `sanitizeRoom()`.

**The landing page's Profile panel *is* the identity step — there is no "play as guest" door.** Guest is the default path, so `LandingHero` asks the two questions it needs (character, name) and START goes straight to the router; signing in is the exception and lives in the CRT header (`headerExtra` from `page.tsx`, top right) rather than inside the panel, so nothing in the Profile panel competes with START. Its icon is a generic grey bust drawn inline, deliberately **not** one of the 12 roster characters — a real character there reads as a specific player rather than as the account you haven't signed into. The mechanism for a guest is that START writes `imposter_guest_name` / `imposter_guest_avatar`, the same two localStorage keys `/dashboard`'s guest gate reads — so that gate falls through instead of asking the identical questions a second time. It is still there, and still reachable by anyone who lands on `/dashboard?guest=1` without passing through the landing page. Change one side's key names and the gate silently starts double-asking.

**A signed-in player sees the same page — the redirect is gone, and the panel switches stores rather than switching off.** `page.tsx` used to `redirect('/dashboard')` on a session, which made the app's one place to change a display name and character unreachable for exactly the players whose identity is worth keeping, and made `/dashboard`'s own "◀ RETURN" bounce you straight back where you came from. Four things follow. Identity is passed **from the server as the `account` prop**, not read with `useSession()` in the panel, so a signed-in name and face are in the first paint rather than arriving a frame later over an empty field — and seeding `useState` from a prop is safe where seeding from `localStorage` or `randomAvatar()` is not, because both renders see the same value. The guest-key read in the mount effect is **skipped when signed in**, or the panel would show the face of a guest this browser used to be and then START would write it to the account. START routes to `/dashboard` **without `?guest=1`**, since that flag is what puts the guest gate in front of the router. And the header's SIGN IN button is now conditional — `CrtShell` renders the profile chip in that same corner on every `home` route, and a SIGN IN button beside your own face is an offer already taken.

**The panel's baseline is the *session*, not the `account` prop, and the fields are an override on top of it.** The prop is the server's answer at the moment this route's RSC payload was built, and the App Router caches that payload — so saving on `/profile` and navigating back to `/` showed the old name and face until a hard reload. That shipped. `router.refresh()` would only paper over it: the prop is a snapshot by construction, and any other route that writes the profile reintroduces the same staleness. `useSession()` is the live copy instead — `update()` rewrites it in place and every consumer sees it in the same commit — and the prop is kept for exactly one job, covering the window before the session resolves so a signed-in name and face are in the first paint. `dirty` is compared against the live baseline too, or a stale prop makes an unchanged panel offer to save. The **override** (`nameEdit`/`avatarEdit`, null meaning "showing what the account holds") is the other half, and it is why there is no re-seeding effect: copying into state and syncing with an effect repaints once with the stale value first, *and* next-auth refetches the session on window focus, so an unguarded re-seed wipes a half-typed name every time the player alt-tabs. `/profile` is built the same way for the same reasons — the two screens edit one thing and must not disagree about where it lives.

**Both stores are written by the same button, on the same event, and the label is what says so.** A guest's character and name are not committed until START either, so saving an account on any other trigger would be the panel behaving differently for the two kinds of player. Signed in, START `PATCH`es `/api/profile` and then `update()`s the session before routing — skipped entirely when nothing changed, so pressing START to go and play is not a database write. The button reads `SAVE & START ⏵` only while there are unsaved edits; that label is the whole of the promise that the edits are not lost, which is why the panel has no SAVE button of its own — a second control beside START on the screen whose entire job is START. `.access-name-row` is 440px rather than 380 **because of that label**: the button is the variable-width half of the pair and the input takes the difference, and at 380 a 20-character name (the field's own `maxLength`) clipped.

**The header profile chip is in the shell, and `/profile` is the fourth screen in the auth family.** `HeaderProfile` (`src/components/vhs/HeaderProfile.tsx`) renders the signed-in player's face and name top right, opening a menu of PROFILE and SIGN OUT; `/profile` is the character picker and display name, with the email shown read-only because changing the address an account signs in with wants the verification step `/api/auth/signup` does not have. Four things worth knowing. It is in `CrtShell` on **`home` routes only** — the same flag the ad rails and the badge label key on — because it is a route *out* of the screen and the in-game screens already have exactly one deliberate exit; an unlabelled second one beside the room code is what LEAVE exists to be instead. It renders nothing while signed out, so `/login` and `/signup` are unaffected and a guest on `/dashboard` keeps the plain name read-out (that chip is now conditional on *not* being signed in, or the name appeared twice). `z-index: 500` is on `.header-profile` and **not on the header**: the header is a flex item of `#crt-viewport`, which is what makes `.home-scroll-area`'s `z-index: 10` and `.camcorder-hud`'s `100` apply at all despite both being `position: static` — raising the header instead would pull the REC indicator and the corner brackets over the bar with it. And `/api/profile` derives the user from the session, never the body, and re-checks the name bounds and the roster id, so a rename cannot get past what signup enforces.

**Saving a profile needs the `jwt` callback's `trigger === 'update'` branch, or nothing downstream moves.** Sessions are JWTs, so the `User` row is not re-read per request: without it the header chip, the lobby and the socket join all go on using the old name and character until the token expires. Both `/profile` and the landing panel call `update({ name, picture })` after a successful `PATCH`, with the values taken from the API's own response rather than from the form — what lands on the token is what actually got written. Nothing else on the token is writable from there.

**Setup happens inside the lobby, not in front of it.** `/dashboard` is three doors — punch in a private code, browse public tapes, host — in that order, with **browse in the middle seat**: it is the door most people take, and the two that need something from you first flank it. **HOST formats the deck on click with no form in the way**. `HOST_DEFAULTS` in `dashboard/page.tsx` is the whole of what a new room starts as (public, text chat, public ballot, memes); it only has to be the least surprising round rather than the right one, because every value is editable from the lobby a second later. The public list is a view *behind* the browse door rather than half the screen, so the router fits without scrolling. The three doors are laid out from `dashboard page.png` — tall portrait cards side by side, full-bleed colour, title set large across the bottom over a scrim, illustrated with the roster art from `public/avatars` so the card and the character you picked on the landing page are the same drawing. Two deliberate departures from that reference: its middle card is taller because quick-play is its one primary action and ours are three peers, and its leftmost card is the player's own profile, which lives on the landing page here. The private card is a `<div>`, not a `<button>` — it holds the code input, and a tile that is itself a button swallows the click that focuses the field.

**The router sits on the landing page's panel.** The three doors are cards *on* something, not tiles floating on the field: `.gartic-main-box.router-box` is plain `.gartic-main-box` — same fill, 4px rim, 24px radius, 12px drop — and overrides only the padding, since the landing box reserves 64px at the top to clear a floating logo this route doesn't have. The two screens a player meets first are then made of the same thing. (An earlier pass dissolved this box to make the router one flat field; that is reversed. The fill is near-identical to `--field` either way, so in dark mode the panel reads by its rim and its drop, exactly as the landing box does.) Two things it depends on. `.gartic-hero-section` (the wrapper *around* the box) stays dissolved on this route — only one level may frost, and in light mode the section is a glass panel that would otherwise draw a full-width band behind the box; that rule sits at the very end of globals.css since it has to out-rank `:root[data-theme='light'] .gartic-hero-section`. And the light-mode bevel is keyed on `#hero-section .gartic-main-box`, which this route is not inside, so `.router-box` is listed alongside it — without that, light mode draws the flat grey outline that block exists to replace.

`LobbyScreen` is laid out from the reference shot in the project root (`example lobby.png`): roster of VCR consoles on the left, options on the right, LEAVE / INVITE / ROLL TAPE across the bottom. The room code rides on the INVITE button — the sleeve card is gone, and the thing you read the code for is now the thing you press. INVITE is off the neon palette: `.lobby-invite-btn` is a near-white gradient with the card ink, as in `lightmode.png`, because a third saturated colour beside LEAVE and ROLL TAPE made the row read as three equal decisions. It is a colour class in vhs.css's sense — `.btn-brutal` supplies no background or shadow of its own, so replacing `cyan` means supplying background, colour *and* box-shadow — and the `.lobby-invite-code` chip has to invert with it, from a dark patch to a light one, or the code disappears into the button. The right panel is two tabs: **GAME MODE** is §4's five genres as icon cards, which is the only choice most lobbies ever make and so gets the space; **CUSTOM SETTINGS** holds the rest of the OSD rows. The custom-content panel renders under the mode grid rather than in the other tab, because what it holds — two links, or two cards — is content for the round rather than a rule about it, and it modifies the card you just pressed. A non-host's mode card is `disabled` rather than hidden — the lobby has to agree on what it is about to watch.

**CUSTOM SETTINGS is built from the lobby's own parts, not from `.osd-menu`.** vhs.css's `.osd-menu` is a literal VCR on-screen display — flat `#0000aa`, white hairlines, monospace — which is right where something really is an overlay on a tape and wrong as a panel sitting beside the mode grid. The tab is now `.setting-row` cards in the same language as `.mode-card`: dark fill, 3px black border, offset shadow, Lilita label, neon-magenta for the chosen option. Three things worth knowing. The binary rows are **segmented pairs rather than one cycling button** — a button that says `TEXT` never says what pressing it will do, and both options on screen also make the 2-suspects lock visibly locked. `.setting-choice-btn.active` marks its pressed state by swapping the drop shadow for an inset one rather than sliding `translate(2px, 2px)`: two small buttons shoulder to shoulder just end up with mismatched baselines. (`.mode-card.active` used to carry that slide and no longer does — it marks selection with a green border instead, see below.) And a non-host gets `.setting-value` — the value as plain text — rather than a disabled control, because they still have to be able to read what the lobby is set to. `.osd-menu` stays in vhs.css and is still used by the shop, the results screen and `VideoSetupPanel`.

**The roster scroller is deliberately wider than its panel.** `.lobby-roster-list` carries `margin: 0 -18px` to bleed out through `.lobby-panel`'s side padding, so the scrollbar rides the panel's inner edge instead of sitting against the consoles; the bar is then pinned to `8px` with `::-webkit-scrollbar` and that 8px is added back as extra `padding-left`, because a scrollbar takes its width off the *right* of the content box and would otherwise leave every console half a bar left of centre. `scrollbar-gutter: stable` holds the reservation whether or not the list currently overflows, so the lobby doesn't shift sideways as the third player joins. All four numbers are load-bearing together, and the MOBILE block has to undo the negative margins — there the list doesn't scroll at all, so they would just hang the consoles outside the panel.

**`.lobby-tab-body` reserves the scrollbar on both edges, and that is the same fault as the roster's, caught later.** The mode grid overflows in every lobby, so the global 8px bar came out of the right side only — and with the hand-rolled `padding-right: 4px` beside it, the cards sat 12px left of centre, flush against the panel's inner edge, while the tab strip above them (which does not scroll) still spanned the full width. `scrollbar-gutter: stable both-edges` mirrors the reservation instead of padding the other side by hand, which is also what stops the panel shifting sideways when you switch to CUSTOM SETTINGS, whose content does not scroll. **Headless Chromium cannot see this class of bug**: it draws overlay scrollbars that take no layout space, so the gaps measure 0/0 and look correct. Measure in a headed browser.

**Ads live in the gutters, and only where there is a gutter.** `AdRail` (`src/components/ads/AdRail.tsx`) is a 160×600 skyscraper that CrtShell renders on the **`home` routes only** — landing, dashboard, auth, shop. The in-game screens are full-bleed and have no empty space beside the content, so an ad there would sit on the round rather than beside it. The rails are absolutely positioned against `#crt-viewport` (which is `position: fixed`, so it is the containing block) and are **siblings of `.home-scroll-area`, not children** — inside it they would scroll away and break the `margin-block: auto` centring. Three things worth knowing. Whether a rail shows is a **CSS** decision, not a React one: `.ad-rail` is `display: none` until the viewport clears `content + 2 × (160 + 24)`, which is 1680px for the 1280-wide boxes and 1400px on `/dashboard`, whose box caps at 988 — keyed on `.router-box` the way that route's other exceptions are. The AdSense script is loaded once from `layout.tsx` and **only when `NEXT_PUBLIC_ADSENSE_CLIENT` is set**, because with no publisher id the tag 400s on every page. And the `adsbygoogle.push({})` is guarded twice, by a ref *and* by the element's own `data-adsbygoogle-status`, since React Strict Mode double-invokes the effect in dev and a second push for the same `<ins>` throws. With no id configured, dev renders a dashed placeholder (so the reserved space is visible while laying a screen out) and production renders nothing. This is an addition to §13, which specifies interstitials and rewarded ads rather than banners; neither of those is built.

**There is no page footer.** CrtShell used to close every `home` route with a copyright strip; it added a second bar to a screen whose whole frame is already a bar. The `.home-scroll-area` wrapper stays — it owns the scroll and the auto-margin centring below — and the `:not(footer)` that centring rule used to carry went with the footer.

**Content boxes are centred with auto margins, never `justify-content: center`.** `.home-scroll-area > *` gets `margin-block: auto`, which centres the landing/dashboard/auth/shop box in the viewport. The reason for auto margins specifically: an auto margin absorbs only *positive* free space, so a page taller than the viewport (the shop) falls back to flush-top and scrolls normally. Centring a scroll container instead puts the top of tall content above the scrollable area, where it cannot be reached.

`.lobby-layout` is both the grid *and* the outer box: capped at 1180px, centred, and **wearing `.gartic-main-box`'s skin** — same fill, same 4px rim, same 24px radius, same 12px drop in dark mode; same bevel, tint and frost in light. The landing page, `/dashboard`, `/login`, `/signup`, the 404 and the lobby are all "one box on a field", and they are one object rendered six times rather than six boxes that happen to sit in the same place — every one of them is a dissolved `.gartic-hero-section` holding a single `.gartic-main-box.router-box`, except the lobby, whose grid *is* the box. **`/login` and `/signup` used to be `.modal-card`**, which was the wrong object twice over: a dialog treatment on a page that is not a dialog, and `.modal-card` carries `transform: translateY(-20px) scale(0.95)` that only `.modal-overlay.active-modal` resets, so outside an overlay both pages rendered permanently 20px high and at 95%. `.modal-title` / `.modal-subtitle` are standalone and came across unchanged: dark-mode fill and rim live on `.lobby-layout` itself, and the light-mode rule at the foot of globals.css lists all three selectors together. Keep them together. This replaced a lavender 3px stroke over a 55px soft shadow, argued for on the grounds that a hard rim plus an offset shadow makes a sticker and reads as a mistake at the size of a whole screen; the landing box is the same size class and has carried exactly that since it was built, so what actually read wrong was the lobby being the only screen doing something else.

**The lobby's height chain is load-bearing and easy to break.** `.view-panel.active-view` is a flex column owning the page scroll, so `.lobby-layout` takes `flex: 1` and its first grid row is **`minmax(0, 1fr)`**. That zero minimum is the point: a grid row defaults to `min-height: auto` and refuses to shrink below its content, so the two panels grow past the viewport and push ROLL TAPE off the bottom of the screen instead of scrolling inside themselves. That was the first state of this screen. Every panel and scroller in the chain carries `min-height: 0` for the same reason, and the MOBILE block has to undo the whole chain — not just the two scrollers — or the stacked panels get squeezed to nothing.

**A mode has a *style*, and the style decides the shape of the round.** `ModeStyle` in `src/lib/videoCategories.ts` is `video | word | question | draw`. The five video genres watch a clip; **Words** deals everyone a word and the suspect a different one; **Questions** deals everyone a question and the suspect a different one; **Fake Artist** deals everyone the same word and tells one player they are the fake. `modeStyle()` / `isPromptStyle()` / `isDrawStyle()` are the lookups — and note `isPromptStyle()` names the two card styles explicitly rather than testing `!== 'video'`, which was correct only while the union had three members and silently misclassified Fake Artist the moment it gained a fourth — branch on those, never on the mode id, or every new mode has to be added to a list of string comparisons. Note the wire field is still `settings.videoCategory`: it dates from when every mode was a video, and renaming it would ripple through `RoomState`, `RoomPublic`, `room:updateSettings` and both screens for no behavioural gain. Read it as "mode id".

`MODE_GROUPS` is the same list sectioned for the lobby, and the sectioning is down to **two** groups: **GAMES** first, then **VIDEOS**. The split that matters to a lobby is whether there is a tape to watch at all, because that decides whether the next five minutes need everyone on one screen; a word, a question, a canvas, a scale and a dictionary are all a card on your own screen and belong under one heading. Four separate headings for those said they were four different kinds of thing when the only choice being made is which one. Videos sit at the bottom because the video genres were pushing everything else below the fold of a panel that scrolls.

**`.mode-card` is width : height = 1.8 : 1, which means `aspect-ratio: 1.8 / 1` — and the mode grid scrolls, deliberately.** This reverses an earlier rule that every group had to clear `.lobby-tab-body` without scrolling. `aspect-ratio` takes width/height, and a landscape brief written straight in as `4 / 6` once produced a portrait tile — check the orientation of the rendered card rather than the number. **No width is set on the card**: `.mode-grid` is `repeat(3, minmax(0, 1fr))`, so three even tracks decide the width and the ratio takes the height from it. The `minmax(0, …)` matters — a bare `1fr` floors at its content, so one long mode name would widen its column and the three cards would stop being the same size. At three columns a card is ~234px wide and ~130px tall, putting about three rows in view and the rest below the fold. **If the tiles should be smaller, change the column count on `.mode-grid`, not the ratio.** The reference does the same — its presets panel has a visible scrollbar and its bottom row is cut mid-card, which is what signals there is more below. **What has to be preserved is now that the cut is visible, not that there is no cut.** The icon is 3.6rem and `flex: 1` so it fills the tile with the label pinned under it; a small glyph floating in the tile reads as a rendering failure. The per-group blurbs were dropped earlier and stay dropped. Measure rather than eyeball — the overflow is silent, because the panel scrolls. The MOBILE block drops to two columns and sets **no `min-height`**: one would beat the ratio at ~165px wide and leave phone cards taller than desktop ones, so the icon shrinks instead. Below 900px tall the panel scrolling internally is the designed fallback, not a bug — that is what the `min-height: 0` chain is for.

**The chosen mode is marked with a closed ring, not a fill.** `.mode-card.active` is `box-shadow: 0 0 0 3px #a3ffb9` and keeps its own background; it does *not* translate. (Light mode repaints the ring pink — see the light-mode section.) Three things about that one line. The green is sampled from `lightmode.png` — the mint that marks the chosen preset there. The **spread** is what closes the ring: `4px 4px` is an *offset* shadow, so a green drop shadow marks the bottom and right edges and leaves the top and left looking unmarked, which is what the first version did; `0 0 0 3px` puts the same band on all four sides. And the chosen card deliberately has no drop shadow and no hover lift — it is already pressed — which is why `.mode-card.active:hover` restates both (the hover rule is more specific than `.active` and would otherwise pull the black offset shadow back under the pointer).

A magenta fill re-coloured the whole tile before this, so the selected card read as a different kind of object instead of as one of ten. `.mode-card` is likewise no longer in light mode's magenta-fill list.

**The two illustrated cards — `.mode-card` and `.deck-card` — look identical in both themes**, and that is the same call made twice: a card whose whole face is artwork keeps its dark-theme fill, because the fill is what the art reads against. Turning the dashboard's three doors white replaced three full-bleed gradients with three white rectangles and the character illustrations lost their ground; `.deck-card-title` / `.deck-card-note` stay off the card-ink list for the same reason, since white text is what those saturated fills want. `.mode-card` is the other half of that rule — dark fill, black border, black offset shadow, `border-radius: 8px` — and it takes no light-mode colour rule at all. That is deliberate, not an omission: the mode grid is a wall of illustrated tiles, and turning them white left ten bright icons floating on ten white rectangles with nothing holding them. The dark fill is what the icons read against, and the black rim is what the green selection ring reads as a ring against rather than as the card's own edge. So in light mode this is a dark card on a purple panel — it separates by *value* where the other cards separate by fill. Don't add it to the white-card list to make that rule tidy. It stays in the *solid* list (no `backdrop-filter`) for the same reason the white cards do: a frosted tile picks up the panel's tint and stops being a flat backdrop.

**The card label is dark ink with a white halo in both themes** — eight 1px `text-shadow`s around `#2f0968`. Both halves are load-bearing. `-webkit-text-stroke` draws inside the glyph and closes up the counters at 0.85rem, so the outline is shadows. And the ink has to be dark *on the dark card too*: the label used to be `#fff` there, and a white outline on white text rendered the whole GAMES group as unreadable mush. The halo is what carries the label on the dark fill.

**A prompt round is not a video round with the video removed.** There is nothing to buffer, so no `game:syncReady`; nothing to synchronise, so no `game:play` and no `room.playAt`; nothing to finish, so no `game:videoEnded`. `PromptScreen` renders inside the CRT frame rather than full-bleed, because the lockdown that justifies going full-bleed has nothing to lock down. The §6 grace still exists but is armed at `game:start` instead of off the imposter's tape ending, and runs `PROMPT_READ_SECONDS` (45s, vs 10) — the card *is* the phase, and it has to be long enough to think of an answer to a question. Everyone clicking Ready still ends it early. `readyGraceSeconds()` is the one place that difference lives.

**`content/prompts.json` pairs are authored, never assembled — this is the whole design of that file.** `pickVideoPair()` draws two independent clips and they are comparable because the genre made them comparable. Two independent *words* are not a game: BEACH against PHOTOSYNTHESIS is over on the first clue. A pair only works when the honest answers overlap, so `normal` and `imposter` are written together and `pickPromptPair()` returns them together. Nothing may take one half of one pair and one half of another. `src/server/promptLibrary.ts` is server-only for the same reason `videoLibrary.ts` is, mirrors its mtime-cache behaviour, and shares `room.usedVideoIds` for no-repeat — pair ids (`w-…`, `q-…`) cannot collide with YouTube ids, so one history covers both.

**The secrecy invariant covers `room.prompts` exactly as it covers the URLs.** It is server-only, `sanitizeRoom()` never carries it (that object is built field by field rather than spread, which is what keeps this true by default), and **`assignmentFor()` is the single point either half is allowed to leave the server** — used by both the live deal and `sendCatchUp`, so a reconnect is not a way to see the other card. `GameAssignment` sets exactly one of `videoUrl` / `prompt` and still has no role flag. Both halves become public in `game:results` (`normalPrompt` / `imposterPrompt`) and not one moment earlier: comparing the two *is* the reveal. Nothing in `PromptScreen` may vary with the card's text — a length breakpoint or a colour by keyword would be a role tell in the one place the game cannot afford one; the question/word size switch keys off the *mode*, which both halves share.

**Fake Artist is the one mode where a player learns their own role, and the invariant narrows rather than breaks.** `ModeStyle` gains `draw`; everyone is dealt the same word, one player is told they are the fake, and `settings.themeHint` decides whether they also get the category. The rule that still holds without exception is the other half: **nobody learns anyone *else's* role.** `imposterIds` never rides a broadcast, `sanitizeRoom()` never carries `room.drawWord`, and `assignmentFor()` is still the single point either half leaves the server — the crew get `drawWord` and no theme, the fake gets `isFake` plus the theme and never the word. Handing the crew the theme as well would tell them exactly how much the fake knows, which is the difficulty the host just set. `themeHint` itself *is* broadcast, because everyone has to know whether the fake is drawing blind: it changes how damning a bad stroke is.

Three things about the implementation. **The turn engine is shared, not copied** — `beginTurnPhase()` backs both `words` and `drawing`, so `wordsUsed`/`wordsPerPlayer` count strokes on a draw round; the names stay for the same reason `settings.videoCategory` still holds mode ids. `startTurnTimer()` therefore captures the phase it was armed in rather than testing `!== 'words'`, or a drawing turn's first tick clears its own timer and the round parks on player one. **A draw round has no watch phase and no Ready Check** — `game:start` runs `beginDrawPhase()` and goes straight to the canvas, because the card is on your own screen for the whole phase rather than read once. And **`skipsWordPhase()` exempts it**: the distinction is *typing*, not turn-taking, and skipping the drawing would leave the round with no evidence to vote on, which is not a shorter game but a broken one.

`room.strokes` is unlike `room.words`: it is not only for reconnects, it *is* the board. Points ride the wire normalised 0..1 (a phone at 390px and a laptop at 1440px must agree on the picture), the server clamps to that range and caps `STROKE_MAX_POINTS`, and stroke colour is derived from the player's seat in `turnOrder` rather than stored — so it survives a reconnect with no extra field and every client replaying the array paints it the same. `DrawScreen` repaints from the whole array on every change rather than appending, because a resize, a replay and a late arrival all have to produce one picture and an append-only canvas cannot. `.draw-canvas` needs `touch-action: none` or a drag on a phone scrolls the page instead of drawing. The card and the turn order are siblings of `.draw-main` in a grid-areas layout purely so the mobile breakpoint can order the card *above* the canvas — nested, you had to scroll past the drawing to re-read your own word.

**A round now ends in one of two shapes, and `GameResults.kind` is what says which.** `'accusation'` is everything built so far — a hidden role, a ballot, an ejection. `'score'` is Wavelength: no imposter, no vote, no reveal, just a table. A discriminant field rather than a union type, because `GameResults` is threaded through the socket layer, the wallet, `room.lastResults` and a large results screen, and splitting the type would touch all of them to express what one field and one branch cover. `finalizeSpectrumResults()` is a **sibling** of `finalizeResults()`, not a branch inside it — they share only the last three lines (stash, broadcast, bank), and five `if (scored)` guards threaded through the accusation builder would make both harder to read. `ResultsScreen` gates the banner, the cassette eject, the verdict card and the vote tally on `kind === 'accusation'`; a scored round rendering them says "TAPE EJECTED", ejects nobody, and shows a tally of all zeros. Branch on `isScoredStyle()`, never on a mode id.

**Wavelength's secrecy surface is a split, not a secret.** The spectrum is **public** — it rides `sanitizeRoom()`, because everyone is guessing on that scale and has to see it. What is held is `room.spectrumTarget` and `room.psychicId`, neither of which ever leaves the server except through `assignmentFor()`, which deals `{ isPsychic, target }` to exactly one player and `{}` to everybody else. The empty object is deliberate: an absent `game:assigned` would itself say who the psychic is. `WavelengthScreen` renders the target marker only when `assignment.target` exists, with **no hidden placeholder** — an element positioned for everyone is a target anyone can read out of devtools. Live guesses are counted but never published (`game:guessTick` carries `guessesIn`, never the values), or every player after the first would just copy the leader.

Two more things worth knowing. The **psychic is not an imposter** — `room.psychicId` is its own field and `imposterIds` is emptied on a spectrum round, because the results screen reads `imposterIds` as "this player was hiding" and the reward table reads it as a side to pay. And the psychic must be picked **before** the `game:assigned` deal loop in `game:start`, not in the phase block after it; picking afterwards dealt every player the empty non-psychic assignment and the mode silently had no psychic at all.

**Bluff Definitions is the second scored mode, and its ballot is the one that does not vote for a player.** An obscure word goes public, everyone writes a fake definition simultaneously (`writing`), then the room votes on which of the entries is real (`bluffvote`). Three structural differences from every other phase. The submission is **simultaneous, not turn-based** — the word phase's engine is no help here and is not reused. The real definition **has no author**, so it rides the ballot under the `REAL_DEFINITION_ID` sentinel (`__real__`, prefixed so it can never collide with a `crypto.randomUUID()` player id). And **ballot options carry `{ id, text }` and nothing else** — attaching an author is the one thing that would end the round, so names appear only in `GameResults.bluffReveal`. The option id doubles as the author's player id, which is what lets the server refuse a vote for your own fake without the client ever being told whose is whose. `beginBluffVote()` shuffles the order **once** and stores it: the truth must not sit in a predictable slot, and two clients showing different orders makes "the third one" unsayable in chat. Scoring pays both halves — `POINTS_PER_FOOL` (2) per player your fake caught, `POINTS_FOR_TRUTH` (3) for finding the real one — so a good writer and a good reader both earn, and doing both wins.

**Light mode is dark mode's structure with a sampled palette — same layout, same borders, same offset shadows, only colour differs.** `data-theme` on `<html>`, toggled from `ThemeToggle` in the shell. **Light is the default** — `layout.tsx` renders `data-theme="light"`, so that is what a first-time visitor gets — and the inline script in the same file applies a stored preference before first paint; without it, a player who chose the other theme gets a frame of this one on every navigation. `viewport.themeColor` follows the default (`#4f079b`, the header): it is one static value for a two-theme app, so it can only match one of them. `className="dark"` also sits on that `<html>` and is *not* the switch — it is Tailwind's dark-variant hook, and nothing in `src/` uses a `dark:` utility, so it selects nothing either way. Two earlier attempts restyled the *shapes* as well and both read as a different app; don't.

Every value came from `lightmode.png` (the Gartic Phone lobby) by **scanning regions for their darkest and lightest pixel**, not by sampling single points — points land on anti-aliased edges and lie, which is how a first pass read a card's border as `#b6a6d0` when the ink is `#2f0968`.

```
page gradient  #722de9 -> #6a00be     card fill  #ffffff -> #d4c4fc
panel fill     #4f079b                card edge  #f0e8fe
panel edge     #8140d7  <- --border-color        card ink   #2f0968
heading green  #a3ffb9                button     #2f0968
empty slot     #4c0ea3, text #7956d5
```

**Light mode runs one accent, and it is the pink.** The reference's mint was sampled and then dropped: `--neon-green` is `#ff5fa2` under `data-theme='light'`, the same value as `--neon-magenta`, so everything the dark theme paints green — ready consoles, the active lobby tab, section headings, the equipped-item ring, the psychic label, the coin bonus — comes up pink there. The name stays `--neon-green` because vhs.css and a dozen components read it by that name; read it as the accent slot rather than as a colour. Three greens are hard-coded outside the var and so are repainted by their own light-mode rules: `.mode-group-title`/`.lobby-panel-title`, `.lobby-tab.active`, and `.mode-card.active`'s selection ring (whose `:hover` variant has to be restated at matching specificity, or the ring flicks back to green under the pointer). The one thing this costs: the "content loaded" ticks in `VideoSetupPanel`/`CustomContentPanel` are green-for-set against `#ff5577` for-missing, and pink against that red is a much weaker signal than green was. If that matters, give those two a colour of their own rather than reintroducing the mint.

**`--border-color` is the highest-leverage value in the file.** `vhs.css` draws every 4px border *and* every offset shadow from it, so one property recolours the entire outline system.

The structural rule the reference implies: **panels are purple and cards are white.** A panel is furniture you read past, a card is a thing you press. Keeping that split is what stops the screen becoming either a wall of white boxes or an undifferentiated purple field. The exception is the two *illustrated* cards, `.mode-card` and `.deck-card`, which keep their dark-theme fills in both themes and separate by value instead — see below. Text inside a white card has to be listed explicitly (`.mode-card-name`, `.setting-label`, `.deck-card-title`, …) because most of those set their own colour for the dark theme.

Three traps, all hit at least once:

- **Containers are not cards.** `.view-panel`, `.home-viewport`, `.home-scroll-area` must stay `transparent`. A fill on `.view-panel` covers the whole viewport and the theme collapses.
- **`#crt-viewport` is an ID selector in vhs.css**, so `:root[data-theme='light'] .crt-viewport` loses to it — match `#crt-viewport.crt-viewport`. Check specificity before assuming an override landed.
- `.draw-card`, `.bluff-word-card` and `.osd-menu` keep their own colours in both themes. The first two hold a secret and a light card is easier to read over a shoulder; the third is a screen within the page.

garticphone.com itself cannot be sampled — Cloudflare blocks automated browsers. `lightmode.png` in the repo root is the source of record.

**The glass layer is light-mode only, and that is a constraint rather than a taste.** `backdrop-filter` blurs what is *behind* an element, so it needs a background with variation to read as glass. Light mode has the gradient; dark mode is near-flat, where a frosted panel is indistinguishable from a solid one and costs a compositing layer for nothing.

Three things make it look like glass rather than like opacity: `blur() saturate()` together (the saturate is what stops the blurred purple going grey), a bright `inset 0 1px 0` along the top edge as the specular highlight, and a translucent light border instead of the solid `--border-color`. The offset drop shadow stays — it is what keeps the brutalist identity.

**The tint is deliberately thin — roughly half what it was** (panels `0.2`/`0.26`, `.lobby-layout` `0.15`, `.vhs-player` `0.26`, the landing box `0.24`/`0.3`). The fill is the one value that decides how much ground reaches the screen, and at full strength the panes sampled the page gradient and the field's halftone bands instead of letting them through. It is not zero, and going to `transparent` was tried and reverted: with no fill the lip reads as an outline drawn on the page rather than as the edge of a pane, and the blur behind it has nothing to be behind. Anything nested keeps its *step* rather than its number: two levels at one value read as a flat field with a hairline across it, whichever value they share.

**The frames are the exception, and they go the other way: darker than the ground, not lighter.** `.lobby-layout` (`rgba(24,6,62,0.34)`) and `.gartic-main-box` (`rgba(30,8,74,0.34)` → `rgba(18,4,54,0.4)`) are recesses the panels are set into rather than lit panes over the page. Two things had to change together on the box, and the second is the one that isn't obvious: the tint moved from a light violet to the page's own deep purple, **and the `saturate()` came down from 180% to 115%**. The saturate boosts the blurred backdrop, so the box came out brighter and more saturated than the field around it however dark the tint over it was — a darker `rgba` alone does not fix a frame that reads too light. This inverts the reference's frame-lighter-than-its-panels structure, so the landing `.gartic-panel`s flipped to the light side of the step with it (`rgba(122,68,202,0.4)` → `rgba(84,34,158,0.46)`). Those blend against the **box**, not the page, which is why their tint has to be much lighter than it looks like it should be to lift at all.

**The header is the exception: bottom edge only.** It is a bar flush to the viewport, so the glass block's `border-width` drew a pale rim across the top of the screen and down both sides, separating the bar from nothing. Light mode zeroes the top and side widths and drops the specular highlight with them — the highlight is an `inset 0 1px 0`, i.e. the same pixel row as the top border, so keeping it would draw that edge back in a different colour. Note that a width alone is enough to render a border here: Tailwind's preflight has already set `border-style: solid` on every element, which is why the glass block never mentions a style. The panels keep their highlight; only the header sits where the two coincide.

**The landing page is one field in light mode, not a band on a ground.** `.gartic-hero-section` is a glass panel, and on `/` it is very nearly the whole screen — so light mode drew a bright purple band with the darker page gradient showing as a strip above and below it, two purples stacked with a seam at each end. The band's colour is promoted to the page and the band itself dissolved, rather than the band being dropped to reveal the ground: the light tone is what this screen is meant to look like. **That gradient is now the light theme's page background on every route**, declared up with the theme rather than keyed on `:has(#hero-section)` at the foot of the file. It was landing-only at first, on the argument that the other screens wanted a darker ground for their panels to read against; the cost was that `/` was a visibly lighter app than `/dashboard` and walking between them looked like a bug. The panels read fine on it — they are darker than it, which is the direction the reference works in anyway. What is still keyed on `#hero-section` is only the genuinely landing-specific half: dissolving the section so the box is the one thing on the field. The gradient stops are tuned so the *rendered corners* match what the band used to composite to, which is why the start reads lighter than any sampled pixel: a `160deg` gradient line starts off-canvas, so the top-left pixel is already some way along it. Check corners, not stop values.

**With the section dissolved, `.gartic-main-box` is the landing page's glass, and its edge is a bevel rather than a line.** It was never in the glass list, so it kept a flat 4px `--border-color` stroke over a 12px pale offset band and read as a grey outline drawn around a dark slab. Scanning across `lightmode.png` — not sampling points — shows the reference draws three things at every edge: a few pixels of soft darkening outside (`#5c1cb3` shading down from the `#6f1bdd` field), a bright 2px lip (`#7e3ed4`), then the interior; its panels repeat it at `#46078f` → `#8140d7` → fill. So the box gets a translucent light border for the lip, an `inset 0 1px 0` specular along the top, and an unoffset blurred shadow for the shading — the offset drop shadow stays underneath in translucent ink, since it is what keeps the brutalist identity. The fill goes translucent with it, because a bright lip on an opaque slab is just an outline: the blur behind it is what the lip is the edge *of*. The two `.gartic-panel`s inside take the same bevel and **never frost** — nested glass doubles the tint and goes opaque. They used to be a step *darker* than the box, as the reference stacks them; the box is now the darker level (see the frame note above), so the step runs the other way and the panels take the light side of it. Landing-only (`#hero-section`), light-only; dark mode keeps its black rim and hard shadow.

**Only one level may frost, and that level is the frame.** Nested glass doubles the tint and goes opaque, so `.lobby-layout` / `.gartic-main-box` frost and the panels on them do not — which is how the landing page has always been built, and the lobby now matches it (`.lobby-panel` takes `#hero-section .gartic-panel`'s fill and lip verbatim, so a lobby panel and a landing panel are the same object). The frost used to sit on the panels instead, and the rule was written as `:root[data-theme='light'] .lobby-layout { backdrop-filter: none }` for a reason worth keeping in mind: the obvious version — `.lobby-layout .lobby-panel { backdrop-filter: none }` — matches *every* lobby panel, because they are all inside the layout. Key these on the class itself, never on the nesting. The white cards also stay solid: they are the thing meant to sit *on* the glass, and frosting them loses the panel/card separation the reference is built on. Scanlines go to `opacity: 0` in light mode — they show through translucent panels and double up.

**Turning text chat off drops the word phase and lengthens the vote.** `skipsWordPhase()` is `chatType === 'none'`, and `startWordPhase()` routes straight to `startDeliberation()` when it is true — including round 2 of a 2-imposter game, or a text-off lobby would get no words in round 1 and a full turn order in round 2. This is the only reading of the 'none' comms mode that holds together: §4 describes it as "we're already on Discord", and a turn-based typing round in a lobby that has deliberately turned typing off is a phase nobody can play. The window becomes `DELIBERATION_SECONDS_NO_WORDS` (180s vs 90) because that lobby now has to do all its talking inside the vote — **read it through `deliberationSeconds(room)`, never the bare constant**, since four separate emits carry `durationSeconds` and a client that gets the wrong one shows a clock that disagrees with the server. Not a setting of its own: it is a consequence of one.

**Video content is split in two, and the split is load-bearing.** `src/lib/videoCategories.ts` is client-safe genre *metadata* only — id, name, icon, blurb — and is what `/dashboard` and the lobby render. The clips live in `content/videos.json` (spec §14: bare YouTube IDs, 10–15 per genre, `label`/`tags` are internal notes never sent to players) and are loaded by `src/server/videoLibrary.ts`, which is **server-only**: the pool is the set the imposter's clip is drawn from, so importing it from a component would ship the answer sheet to the browser. `videoLibrary` re-reads the JSON whenever its mtime changes, so links can be added without restarting the server, and keeps the last good copy if an edit leaves the file unparseable.

`pickVideoPair()` takes the round's genre plus `room.usedVideoIds` and returns two distinct clips, excluding anything the lobby has already seen. `usedVideoIds` lives on `RoomState`, is deliberately **not** in `freshRoundState()` — it must survive a Rejoin — and dies with the room, which is what "resets when the lobby closes" means. When a genre runs dry the helper drops that genre's history and returns `recycled: true`; other genres' history survives, so switching genre mid-lobby doesn't reset the one you were playing. A lobby with custom content on never reaches this: the host's own pair is already on the settings and the shelf is left alone, history included.

**Video playback** — `src/components/game/VideoPlayer.tsx` handles YouTube (IFrame API, loaded once behind a global `window._ytReady` guard), Vimeo (postMessage), and MP4 (`<video>`) behind one imperative `play()`/`pause()` handle; `src/lib/videoParser.ts` picks the type. Sync works by each client emitting `game:syncReady` on load, then the server broadcasting `game:play` with a `playAt` timestamp ~1s out that clients schedule against. Players render with `pointerEvents: 'none'` and no controls. The lockdown player vars the spec asks for in §5 (`controls=0`, `disablekb=1`, `fs=0`, `modestbranding=1`, `rel=0`) are already set. The YouTube branch names its container `#yt-player-container` and its inner div `#yt-player` **on purpose**: the IFrame API swaps that div for an iframe of its own and keeps only the id, so those two vhs.css rules are what size the frame to 100% and apply the `scale(1.15)` that crops YouTube's title bar and control strip out of shot. Rename either id and the video reverts to a 640×360 box in the corner with its title on display.

**Live emoji reactions (§5) are the one event that does not go through `useRoom`.** `game:react` → `game:reaction`, watch phase only. The three-place rule still applies to the *outbound* side (`sendReaction` in the actions object), but the **inbound** listener lives in `src/components/game/ReactionBar.tsx`, subscribing to the socket directly the way `GameScreen` already does for `game:play`. That is deliberate: reactions are ephemeral and arrive several a second from a full lobby, so putting them in the room hook's state would re-render every subscribed screen on each one. Nothing is persisted — a missed reaction is not worth recovering, and `room.words`/`room.lastResults` exist for reconnects precisely because reactions do not.

Three server rules, all in the handler: the emoji is checked against `REACTION_EMOJI` in `src/types/index.ts` (a closed set of five — an open field would be a 300-char chat channel during the one phase with no chat); each player is throttled to one reaction per `REACTION_MIN_INTERVAL_MS`, because the animation paints over video nobody can pause; and spectators are excluded, since the Custom author has no tape playing. The throttle timestamp is `Player.lastReactionAt`, server-only — safe because `sanitizeRoom()` picks its fields explicitly.

**Only the emoji is rendered — not the sender.** The payload still carries `playerId`/`playerName` (it is the room's reaction feed, not one component's props) but the float is the bare glyph, which keeps the corner clean over a video nobody can pause. The consequence for §5's stated side benefit is worth knowing: the tell now rests on *timing* alone — you see a reaction land out of step with everyone else's, not whose it was. Don't "fix" the missing name; it was removed deliberately.

The payload carries nothing role-shaped, so it sits fine beside the secrecy invariant: crew and imposter emit an identical shape. Keep it that way.

**Emoji artwork comes from `--font-emoji`: Apple Color Emoji first, then a bundled subset.** Apple's font is proprietary and licensed to Apple hardware, so it can be *asked for* but never shipped — iPhone, iPad and Mac genuinely render Apple's artwork, and that is the only legitimate way anyone gets it. Everything else falls to `public/fonts/emoji-reactions.woff2`, a **3KB five-glyph subset of Noto Color Emoji** (OFL, licence bundled), so the same reaction doesn't look different on every machine in the lobby. Subsetting is not premature: the full family is ~2MB across its slices and the slice these five fall in is 100–700KB on its own.

**That font is coupled to `REACTION_EMOJI`.** Its `@font-face` declares `unicode-range: U+1f440, U+1f525, U+1f602, U+1f622, U+1f62e` and the file contains only those. Add a sixth emoji without regenerating and it silently renders in the platform font, looking wrong beside the other five — nothing errors. `public/fonts/README.md` has the regeneration command.

**Simulated players fill a lobby so one person can play a whole round.** `src/server/bots.ts` is *what a bot is and says* — names, faces, vocabulary, jittered timings; **when** a bot acts is `runBotTick()` in `socketHandlers.ts`, because acting means calling the same mutators and broadcast helpers a real socket event calls (`setPlayerReady` + the readyCount emit, `recordWord` + `nextTurn`, `castVote` + `broadcastTally`). That split is the design constraint: **a bot must not be able to reach a state a player could not**, or the round it fills is not the round being tested. Reactions go through the shared `broadcastReaction()`, so a simulated reaction is byte-identical to a real one.

A bot has **no socket** — `socketId` is `''`, so every `io.to(socketId)` emit addresses nothing and fails silently. That is fine (a bot needs no video URL, and `game:start` already guards with `!player.socketId`) but it is why a bot can never be driven by "pretend it sent this event". Three consequences worth knowing: `botTimers` is its own map because `roomTimers` is one slot per room that the phase machine already owns; `removePlayer` drops all bots once the last **human** leaves, since bots never disconnect and `players.length` would otherwise never reach zero, leaving a listed, unjoinable, immortal room; and `reformLobby` discards bots rather than parking them in `pastPlayers`, which only exists so a real player can click Rejoin.

**Bots never report `game:videoEnded`** — that event arms the 10s post-imposter grace, so a bot drawn as the imposter would yank a human out of the video seconds in. They click Ready instead, which stops them blocking while leaving the pacing to the human. And **bots bandwagon onto the current vote leader** rather than choosing uniformly: uniform bots are markedly *more* tie-prone than a real lobby that talks and converges, and since §8 re-votes on a tie, a tester ends up in round 2, 3, 4 and never sees the results screen. Observed three consecutive three-way ties before this changed; after it, none.

`BOTS_ENABLED` defaults **on in development, off in production** — this is a way to stuff every open lobby with fake players otherwise. `ALLOW_BOT_PLAYERS` overrides in both directions. The flag rides to the client as `RoomPublic.botsAllowed` rather than a `NEXT_PUBLIC_` var, so the button and the handler cannot disagree about whether it works. `PlayerPublic.isBot` is broadcast on purpose and rendered as a `SIM` badge with `(BOT)` in the name: a lobby has to be honest about which of its players are furniture. Host transfer to a bot is refused **server-side as well as hidden**, because a bot can never press Roll Tape and would strand the room.

**The watch phase is bookended by two tape animations**, both ported from `vhs-frontend-example`. Going in, `GameScreen` runs the prototype's `startWatchSequence()`: the gate drops, a cassette rides up into it, then the overlay fades as `.vhs-starting` blooms the picture on. The prototype drives that off a fixed 1.8s timeline because it has nobody to wait for — here the beats hang off the real sync instead, so the tape "reads" while other decks buffer and the picture powers on at the `playAt` moment. Coming out, `ResultsScreen` toggles `.vcr-deck.ejected` and the cassette flies out of the slot.

Both needed a clearance fix, and **the prototype has the same collision** — verified against it running on :9000, so don't "restore" these to match it. In each case an absolutely-positioned cassette lands on text that was laid out without it: the insertion caption gets `position: absolute` (growing its margin barely helps, since the flex column recentres and takes half of it back), and the results deck gets top margin so the eject's throw has somewhere to go. Both overrides live in the App additions block in `globals.css` with the reasoning inline.

**The wallet has two backings, and only one of them is trustworthy.** `src/hooks/useShop.ts` presents one API over both: signed-in players go through `/api/wallet/*` to `User.coins` / `CosmeticOwnership` / `User.equipped`, guests stay on `localStorage` (`imposter_coins`, `imposter_shop_owned`, `imposter_shop_equipped`) exactly as before. `persistent` on the hook is which one you're on. Guest identity is likewise localStorage (`imposter_guest_name`, `imposter_guest_avatar`).

`src/server/wallet.ts` is the **only** thing allowed to change a balance, and it is server-only — importing it from a component drags Prisma into the browser bundle. Prices come from `src/lib/cosmetics.ts`, never from a request; purchases run in one transaction with the `(userId, itemId)` unique constraint blocking double-owns and a post-decrement check blocking an overdraw across two different items. Every `/api/wallet/*` route re-derives the user from the session, so no request body ever names whose wallet to touch. `buy()` is async now.

**`userId` on `room:create`/`room:join` is ignored.** It is client-supplied, so it was a claim, not a fact — harmless while it only labelled a player, a coin printer now that `finalizeResults` credits real money against it. `src/server/socketAuth.ts` decodes the NextAuth session cookie off the socket.io handshake instead, and `socket.data.userId` is what `Player.userId` gets. It is refreshed on reattach, since someone may have signed in between the drop and the return. `bankRewards()` is deliberately fire-and-forget behind the results broadcast: a database hiccup must not hold up or half-fail the reveal every client is waiting on.

**Guests keep a real wallet that really does evaporate**, which is what §11's claim-your-account prompt is about — it now renders on the results screen after every round, and on the shop. Signing in folds the guest wallet into the account once via `/api/wallet/claim`. That payload is unverifiable by construction, so two things guard it: `User.claimedGuestAt` makes the claim single-use per account, and `MAX_CLAIMABLE_COINS` caps what a hand-edited localStorage can be worth. Coins are added and ownership merged, never overwritten, so claiming can't wipe a balance the account already had.

**The cosmetic catalogue lives in `src/lib/cosmetics.ts`, not in the hook.** It has to be importable by the socket server — which validates incoming ids — and a server that has to import a React hook to check a string is the wrong shape. `useShop` re-exports `SHOP_ITEMS`/`COSMETIC_CATEGORIES` so existing callers didn't change.

**A loadout is broadcast, because a skin only you can see isn't a cosmetic (§10).** The client sends `equipped` on `room:create`/`room:join`; the server runs it through `sanitizeCosmetics()` — which drops unknown ids *and* ids sent for the wrong slot — and puts the result on `Player.cosmetics`, which `sanitizeRoom()` includes and `game:results` repeats. Cosmetics carry no role information, so this sits fine beside the secrecy invariant; keep it that way. `vcrSkinStyles()` / `tapeSkinStyles()` produce the same styles the shop previews use, so what you bought is what you get: VCR skins repaint the lobby consoles and the voting grid, the tape skin and label ride the insertion cassette (your own, straight from localStorage) and the results cassette (the accused's, from the payload). Because it's sent at join time, changing your loadout means leaving and coming back.

**Auth** — NextAuth, JWT sessions, credentials (bcrypt) plus Google/Apple providers conditionally spliced in only when their env vars exist — §11 lists Discord as a later addition, not a launch provider. `src/components/auth/OAuthButtons.tsx` calls `getProviders()` and renders a button only for what is actually live, so an unconfigured provider is invisible rather than broken; `/login` and `/signup` share it, because an OAuth sign-in for an unknown account *is* the sign-up. `APPLE_CLIENT_SECRET` is a signed ES256 JWT that expires within 6 months, not a static string — `scripts/generate-apple-secret.mjs` (`npm run apple:secret`) mints one. The `jwt`/`session` callbacks thread the DB user id onto `session.user.id`, passed as the optional `userId` on `room:create`/`room:join`.

**The stock `PrismaAdapter` cannot create an OAuth user against this schema**, which is why `src/lib/authAdapter.ts` wraps it. Two independent breakages, both reachable only on account *creation* — invisible for as long as credentials was the only live path: there is no `User.image` column, so Google's `picture` reaches `prisma.user.create` as an unknown argument; and `User.name` is required while Apple's id_token has no `name` claim at all. `gameAdapter()` drops the photo, falls back to the email's local part for a name, and deals a `randomAvatar()`. **An avatar here is a generated character, not a URL** (see below), so a provider picture is deliberately discarded rather than stored. The `jwt` callback normalises the code onto `token.picture` from either `user.avatar` (adapter row) or `user.image` (credentials `authorize()`), which is what makes `session.user.image` a character code whichever provider signed you in; `room/[code]/page.tsx` feeds that straight to the socket server.

**Avatars are a fixed cast of 12 illustrated characters, not a composer.** `src/lib/avatars.ts` holds the roster — an id and a display name each — and the artwork lives in `public/avatars/c00.svg` … `c11.svg`. All 12 share one 262×299 viewBox and one ink colour, `#012442`; there are no strokes anywhere, outlines are filled shapes stacked behind fills, in the Illustrator expand-stroke manner.

**The art is authored by `scripts/generate-characters.mjs`, which is a build-time tool, not a runtime composer.** Each character is drawn deliberately; the shared helpers (`oCirc`/`oEll`/`oRect`, `bust`, `eye`) only supply the boilerplate every character repeats, the way Illustrator symbols would. Re-run the script to regenerate the set. **Edit the art there, never in `avatars.ts`** — that file only names what the script emitted, and **the ids are positional against the script's `CAST` array**, so reordering the cast silently reassigns every stored avatar to a different character.

****Artwork from an image generator comes in through `scripts/ingest-avatars.mjs` (`npm run avatars:ingest -- --in <dir>`), never by hand.** A generated SVG is wrong in four ways that are each silent: the canvas is square rather than 262.2×299 (and `Avatar.tsx` sets an inline `height` with `width: auto`, so it renders visibly wider than the cast); fills arrive as `<style>.st0{…}</style>` + `class="st0"`, whose class names are global to the *document* and overwrite each other the moment two files are inlined together; exporter ids are numbered per file, so every file's first clip path is `SVGID_1_` and inlining collides those too; and the ink drifts a few units off `#012442`. The script fixes all four, prints an id→file→name table before writing, refuses to overwrite without `--force`, and emits the `CHARACTERS` array — the ids being positional is exactly why the file list and that array must not be hand-synced. Two things it must keep doing: strip only ids nothing references (clip paths, masks and `<use>` are wired together *by* id, and removing one renders the art unclipped with no error), and re-declare `xmlns:xlink` on the rebuilt root when the body still uses it (an undeclared prefix makes `<use>` resolve to nothing, the clip path empty, and the whole file blank). Both were real bugs, caught by diffing a render rather than by reading the output.

The smoothing core is the style, not an implementation detail.** The first version of the script built characters from primitives and straight lines and read as sharp beside `pfp-examples/` — counted, the reference is 4214 cubic segments and 396 smooth continuations against 13 quadratics, curves beating straight lines about 3:1, while the script managed 34 straight segments, 45 quadratics and zero smooth continuations. Three helpers fix that and **new characters must be built from them** rather than from `path()` with `L`/`q`:

- `smoothLoop`/`loop` — Catmull-Rom through points, emitted as cubics. Joins are C1 by construction, so a silhouette cannot kink at a vertex. `horn` (ears, antennae), `lens` (mouths), `drop`, `tri` and `blobPts` are all built on it.
- `squirclePath`, which `rect()` routes to for any non-zero corner radius. `rect rx` snaps from zero curvature to `1/r` in one step and the eye reads that jump as a corner; the squircle's control factor is deliberately 0.42, below the 0.5523 that would reproduce a circular arc, so the curve peels off the straight edge gradually. Radius 0 stays a real `<rect>` — that's for internal detail like teeth gaps, where there's no silhouette to soften.
- `grow()`, which offsets a loop along the **vertex angle bisector with a miter correction**, not radially from the centroid. Radial is right only on a circle: on a tall shape a flank point is much nearer the centroid than the crown, so one `pad` buys a different outline width at each vertex and the ink reads as a lumpy band. This was actually shipped once and looked it.

Two tuning facts worth not rediscovering. `horn` bulges each flank away from the ear's **own centroid** — pushing along a single axis-perpendicular shears the ear into a lean instead of fattening it — and its tip is two points a hair apart, because the spline rounds every vertex and one tip point domes over. And **inner ears must clear the skull line**: the head blob paints after the ears, so a low inner ear is simply covered, which is not obvious from the code order.

Wobble on `blobPts` is deliberately small (0.012–0.018). It is seeded through `rng()` so regeneration is byte-identical — an unseeded jitter would make every rebuild a diff — and above ~0.02 it stops reading as hand-drawn and starts reading as a lumpy outline at the sizes the game actually renders.

`pfp-examples/` is the user's **reference set only**. It is not shipped and nothing imports it: the style was measured out of it (canvas, badge geometry, ink colour, the two eye highlights at ~0.30/0.18 of the eye radius, blush as an unoutlined plum ellipse, teeth as a white block with ink bars for the *gaps*), and then original subjects were drawn to those rules. That is why the licence question those files raised no longer applies to the build.

The cast is deliberately small — enough to judge the style. Ten-player lobbies want more, and extending it means adding entries to `CAST` **at the end** and appending the matching names to `CHARACTERS`.

**This deliberately replaced a procedural system, and it cannot go back.** An earlier version composed an avatar from five interchangeable slots (colour, body, eyes, mouth, accessory) for 2048 combinations. That premise cannot express this art: a donut, a burger and a luchador mask share no parts. If someone asks for "more variety", the answer is more illustrations, not a return to mix-and-match. Two players in one lobby *can* draw the same character; that is accepted, as it is in Gartic Phone.

The art is served statically, not inlined — it belongs in the static layer where the browser caches per file, rather than in the JS bundle where every player would pay for the whole cast whether they see it or not. `Avatar.tsx` renders a plain `<img>`; `avatarSrc()` builds the path.

`characterFor()` **never throws**, which is what makes this migration-free. **Three** generations of stored avatar flow through it: the emoji that pre-date characters entirely, the `a70312` part-codes from the composer, and ids from the discarded 28-character set. All hash to a *stable* roster character, so an old account keeps the same face on every load and no database backfill was ever needed. `toAvatarCode()` normalises at the socket boundary, `isAllowedAvatar()` is the validator.

Four UI rules worth keeping:

- **The first deal must happen in an effect, never during render.** `/signup`, `/dashboard` and `/room/[code]` are prerendered, so `Math.random()` in a `useState` initialiser bakes one character into the static HTML and picks another at hydration. Each seeds `FIRST_FRAME_AVATAR` (`'c00'`) and deals on mount.
- **The reroll button steps the roster in order** (`nextAvatar`), it does not randomise. Browsing the cast should be predictable rather than a slot machine that repeats.
- **`.character-slot` in globals.css is required wherever a character renders in one of vhs.css's avatar slots.** Those slots supply a white disc, a black ring and a circular mask, all built to frame a bare emoji — against this art all three crop exactly the hats and ears that give a character its identity. The modifier strips the framing and keeps the positioning.
- **Size comes from the `size` prop, never from CSS.** `Avatar` sets an inline `height`, which outranks any selector, so a `.character-slot img { height: 100% }` rule looks correct and silently does nothing. Width stays `auto` so the 262×299 art is never squashed square.

Do *not* put a character in `.player-tag`: that pill is `font-size: 0.6rem` and anything legible bursts out of it. `.player-avatar-circle` is the slot on a `.vhs-player` console, used by both the lobby and the deliberation grid.

**Apple needs a SameSite=None PKCE cookie, and Google does not.** Apple returns with `response_mode=form_post`, so the browser POSTs the callback cross-site from appleid.apple.com and a Lax cookie is not sent — the classic "pkce code_verifier cookie was missing" failure. `authOptions.cookies` overrides `pkceCodeVerifier`/`state`/`nonce`/`callbackUrl` to `SameSite=None`, but **only when Apple is configured and `NEXTAUTH_URL` is https**: SameSite=None without Secure is rejected outright, and Apple won't accept an http or localhost redirect anyway, so Apple is untestable locally by construction. The session cookie stays Lax on purpose — it's set in the callback response and then read on a top-level GET, which Lax allows.

**Email-to-OAuth linking is deliberately off.** `allowDangerousEmailAccountLinking` stays false, so a Google sign-in for an address that already has a password account fails with `OAuthAccountNotLinked`. That's not an oversight to fix: `/api/auth/signup` does not verify email addresses, so auto-linking would let anyone register a victim's address and inherit their Google sign-in. `pages.error` points at `/login`, which maps the `?error=` codes to copy a player can act on.

## Where the code contradicts the spec

Verified against `src/` as of this file's writing. These are bugs-against-spec, not design choices — fix toward the spec column, and don't "preserve existing behavior" here.

**One exception, and it is an owner decision rather than a bug: the lobby floor is 3, not §20's 4.** `MIN_PLAYERS` is 3 in both `socketHandlers.ts` and `LobbyScreen.tsx` (the pair is mirrored on purpose — the server clamps, the client only greys buttons). Everything downstream reads the constant: the empty console slots, the `MAX PLAYERS` floor, the default bot fill, and the start check. The head count now rides on the ROLL TAPE button as `(n/3)` rather than in a note beside it, since it is the answer to "can I press this yet". `MAX_PLAYERS` stays 10 and the 2-suspect unlock stays at 7. A full 3-player round has been driven end to end over sockets, tie-break included; do not "restore" the 4 to match the spec.

Phase 1 (spec §16) closed most of the original gaps. **Fixed and verified:** role secrecy, single imposter, lobby size (3–10, see above), reward values, combined 90s deliberation window, server-authoritative vote timer, split-vote re-vote and tie-break loops, per-player Ready Check, and the `none` comms mode.

Phase 2 is closed. ## Conventions

- Import via `@/*` → `src/*`.
- **Styling is the VHS/CRT system in `src/app/vhs.css`** — a verbatim copy of `vhs-frontend-example/styles.css`, imported first by `globals.css`. Build with its classes (`btn-brutal`, `brutal-card`, `vhs-player`, `osd-menu`, `osd-text`, `modal-card`, `brutal-input`, `view-panel`, `gartic-*`, `lobby-item-*`). Don't edit `vhs.css` — it tracks the reference; app-only additions go in the "App additions" block in `globals.css`.
  - **Outfit's 900 cut is loaded by a `<link>` in `layout.tsx`, and a CSS `@import` cannot replace it.** vhs.css's own @import stops at `wght@400;600;800`; `.router-code-input` is the one rule that wants 900, because a room code is six characters transcribed off someone else's screen and the weight is what tells B from 8 and O from 0. A second `@import` in globals.css looks like the obvious home for it and **silently does not work**: CSS requires @import before any other rule, and webpack hoists the content of `@import './vhs.css'` above globals.css's own body whichever line the sibling sits on, so the request lands after ~3400 rules and the browser drops it — while still leaving it in the compiled CSS, so grepping finds it and the field quietly renders at 800. Both orderings were tried. **`document.fonts.check('900 18px Outfit')` is not the test** — it returns true whenever the weight merely *matches* something, so it reports true against a family that stops at 800. The real check is `[...document.fonts].filter(f => f.family === 'Outfit')` listing a 900 entry, confirmed by the rendered text measuring differently at 800 and 900. The `no-page-custom-font` lint warning on that link is a Pages Router rule misfiring on the App Router's root layout, which does wrap every route; it is disabled inline with that reason.
  - **`--font-marker` no longer holds a marker font.** Permanent Marker is a single-weight handwriting face, and it was doing two different jobs: labelling props that are *meant* to look handwritten (a cassette title, a shop item's name) and setting real UI text — the player's name in the header, the room code on the INVITE button, the fields you paste a URL or type a custom prompt into. It cannot do the second: at 1rem in a header bar it was the least legible type on the screen, and a URL read back in handwriting is close to unreadable. Everything is now the UI face (Outfit), which is what the landing page's name field has always used, and **`.header-profile-name` matches `.access-name-input` exactly** — 600 weight, 0.5px tracking — because the name in the corner and the name you typed are the same thing. Two halves, because vhs.css is not edited: what this app owns names `--font-ui` directly, and what vhs.css owns is redirected at the token, `--font-marker: var(--font-ui)`. Read the name as a **slot**, the way `--neon-green` is the accent slot once light mode fills it with pink. Aliasing beats listing selectors for one reason worth keeping: a rule copied over from `vhs-frontend-example` later cannot silently reintroduce the handwriting face, because nothing is behind that name any more. The swap needs a **weight** with it — Outfit's default 400 is much lighter than Permanent Marker's single heavy weight, so a bare family change reads as though every one of those labels had been de-emphasised; the block at the foot of globals.css puts the five vhs.css-owned classes this app actually renders at 600. Tracking is deliberately not in that block: `.lobby-invite-code` wants its own 3px, since a code is read character by character.
  - **`--field` is the lighter purple, `#2b1063`, on every screen.** The dark theme used to be a dark room (`#1a0b3d`) with lighter boxes floating in it; it is one continuous lighter field now, and the panels sit on it by being *darker* than the ground rather than lighter. `--field-wash` holds the same value on purpose — the radial bloom that lifted the centre has nothing to lift once the field is already the light tone, and keeping the token rather than tearing the gradient out of the two rules that use it makes putting a bloom back one edit. Two knock-ons worth knowing: `--bg-dark` is also `#2b1063`, so anything filled with it (`.brutal-card`, `.shop-item-card`, `.btn-brutal.dark`) now reads by its border and drop shadow rather than by its fill; and light mode is untouched, since its page was already the lighter tone.
  - **The field's dots are packed into diagonal bands, not spread over it.** This is the thing to know, and two earlier attempts got it wrong by guessing: the reference does *not* dot its whole background. It runs **wide halftone ribbons across the screen at ~45°** with plain empty purple between them. Inside a band the dots are a plain staggered lattice — it is the band, and the fade at its edges, that stops the eye reading a grid. Spreading dots evenly does not read as texture at any density or alpha; nor does scattering them across co-prime tiles, which was the second attempt. Measured perpendicular to the band (which is what gradient stops measure, not the wider horizontal slice you see): period ~155px, band ~55px with ~22px fades, dot pitch 14px staggered, dot ~7px. `135deg`, not `45deg` — a 45° gradient's iso-lines run "\" and the reference's run "/". None of this is visible at 1:1; it was read by high-passing the whole frame (subtract a local box mean, amplify ~16×), which is also how to check any change to it. `.field-texture` in globals.css owns it, and it is **an element** because the bands are a `mask-image` and background layers cannot be masked individually — `.crt-viewport`'s own `::before`/`::after` are taken by vhs.css's vignette and scanlines. CrtShell renders it at **`z-index: -1`**: a negatively stacked child paints after its parent's background but before the parent's in-flow content, where `0` or `auto` would paint dots over every screen. Two consequences. The field's old 40px white grid lines are **gone** from `body` and `.crt-viewport` — they were the other fixed-pitch thing on the field and read as the graph paper the bands exist to avoid; the reference draws no grid at all. And the alpha (0.16 in-band) is the one number not copied: the reference's dots are black at ~0.09, but its field is far lighter than ours and 9% of `#2b1063` is a drop nothing renders.
  - **The frames get a grain, and it is deliberately not the field's texture shrunk.** `.lobby-layout` and `.gartic-main-box` — the things the panels sit *inside* — were the one surface with nothing on them, a flat tint between a textured field and textured cards. Both now carry a `::before` overlay: an even 9px staggered lattice of 1.6px white dots, no bands and no mask, at 0.05 (0.08 in light mode). Two things it must not do. It must not repeat `.field-texture`'s 14px banded lattice at a smaller size — two lattices of the same kind at different phases moiré against each other, and the frame sits directly on the field. And the dots must stay **white**: the frames are translucent over purple, so a dark dot punches through the pane and reads as dirt behind the glass rather than as the surface catching light. Even spacing is right here for the same reason it is wrong on the field — a uniform lattice reads as graph paper only at the scale of a whole screen. Implementation: `position: absolute` keeps the pseudo-element out of `.lobby-layout`'s grid (a grid container's pseudo-element is otherwise a grid item and takes a cell), and `z-index: -1` under `isolation: isolate` puts the grain over the frame's own tint but under every panel on it — the isolation is what stops that `-1` escaping to an ancestor's stacking context and sliding behind the page.
  - **The drop shadow goes straight down, never diagonally.** From `lightmode.png`: its buttons and cards are rounded shapes with a hard shadow sitting *directly under* them — a key you press — where vhs.css's brutalism throws the same hard shadow down *and to the right*, which reads as a sticker peeled off the page. Same ink, same hardness, same distance: only the axis changed, and hover lifts became `translateY` to match, because a diagonal lift under a vertical shadow looks like two materials. Everything globals.css owns was rewritten in place (`box-shadow: 4px 4px 0 X` → `0 4px 0 X`); an **EDGE LANGUAGE block at the foot of globals.css** covers what vhs.css owns, since that file is not edited here. That block lists only the classes this app renders — the prototype's remote control, sleeve case and role banner have no markup here — and it keeps each rule's own depth and colour, including the accent shadows (a ready console's green, an equipped item's ring), which have to stay their own colour or the state stops reading. Two traps: the shadow lives on the *compound* `.btn-brutal.yellow`-style selectors, so matching `.btn-brutal` alone silently changes nothing; and being at the foot of the file, that block out-ranks earlier same-specificity rules, which is why anything meaning to remove a shadow has to be compound too.
  - **Every route is ported** — `page.tsx` (landing), `/dashboard` (lobby router), `/login`, `/signup`, `/shop`, `not-found.tsx` (the 404), and all five room phases. The 404 is a `home` route built on `.gartic-main-box.router-box` — the plain `.gartic-main-box` reserves 64px at the top for the landing page's floating logo, and the light-mode bevel is keyed on `.router-box`. It exports no `metadata`: Next reads that only from layouts and pages, and a not-found file is neither. Its colour bars are the SMPTE pattern at broadcast values with **hard stops** — a blended gradient reads as a colour wash, and a test card is its boundaries — and they keep their own colours in both themes, like `.draw-card` and `.osd-menu`. The old violet/glass system is gone: no `glass`, `card`, `btn-primary`, `input-field`, `grid-bg`, or `neon-*` classes remain, and `tailwind.config.js` no longer carries a colour scale. Tailwind survives for layout utilities only (`flex`, `inset-0`, `w-full`); colours come from the `--neon-*` custom props.
  - `<CrtShell>` supplies the viewport frame. Pass `home` for the scrollable marketing/console layout (landing, dashboard, auth, shop); omit it for the in-game `.view-panel` stack. It sets no body classes — `.crt-viewport` is `position: fixed` and vhs.css already locks body scroll, so a page rendered *outside* CrtShell inherits that lock and must scroll an inner container.
  - **Every screen arrives with the same animation, and it is one CSS rule.** `route-enter` (globals.css, foot) rises 18px, scales up from 0.97 and settles with a small overshoot — the overshoot is the whole character, and it lives in the `cubic-bezier(0.2, 0.9, 0.25, 1.15)` third control point going past 1, not in the keyframes. It runs on `.home-scroll-area > *` (the content box on a `home` route) and on `.view-panel.active-view` (the phase panel in a room), so lobby → watch → words → vote → results get it too; that rule replaces vhs.css's `view-fade-in` on the same element by sitting later at equal specificity. Two things not to undo. The fill is **`backwards`, never `both`**: a retained final value is the *interpolated* one and `transform: none` interpolates as an identity matrix, so `forwards` leaves `matrix(1,0,0,1,0,0)` on the element permanently — and an identity transform is still a transform, which makes the panel a containing block for any `position: fixed` descendant. (Measured: `both` computes to a matrix at rest, `backwards` to `none`. vhs.css's own `view-fade-in` has this bug, ending at `translateY(0)` with `forwards`.) And `CrtShell` keys the content subtree on `usePathname()`, because two routes that render the same shape can be reconciled in place and an element that is never re-created never restarts a CSS animation. The key does not fire inside a room — the pathname is the room code there — so phase changes rely on the panel's own mount, which is one per phase anyway. `prefers-reduced-motion` redefines the keyframes to a plain fade rather than removing the animation.
  - **The MOBILE block in `globals.css` is where the app is made to work on a phone**, and its governing rule is that **a value a media query must be able to override cannot be an inline style.** An inline style beats every selector, so `style={{ gridTemplateColumns }}` silently defeats a collapse-to-one-column breakpoint — that was the actual state of the old `/dashboard`, which rendered two crushed columns at 390px while vhs.css's 820px rule sat there unable to apply. If a new screen needs a responsive value, it goes in a class. Heights use `100dvh` behind `@supports`, because mobile `100vh` measures the viewport with the URL bar retracted and puts the bottom row of a fixed frame under the browser chrome. `layout.tsx` sets `viewportFit: 'cover'` (which is what makes `env(safe-area-inset-*)` non-zero) and deliberately does **not** cap zoom — the iOS input-zoom trap is fixed by setting inputs to 16px instead, which costs nobody their pinch-zoom.
  - **Under 768px the header is the mark alone.** The wordmark is `display: none` (it used to be shrunk to 1.4rem with an `!important`, since the `<h1>` carries an inline 2.2rem, and even then it wrapped the bar onto a second line) — the logo image still sits inside `.logo-home-link`, so the link, its `aria-label` and the go-home affordance all survive. The **page label** goes with it: `CrtShell` puts `.header-badge-label` on the badge when `home` is set, which is exactly the routes whose badge is a caption ("LOBBY ROUTER", "SHOP", "NO SIGNAL"), while the room routes pass a room **code** — data, and on the in-game screens the only place it appears. Don't collapse those two into one rule. **And it stays one row.** vhs.css turns the header into a centred column under 768px, which put the mark on one line and the controls on a second and cost ~46px of the shortest screen in the app; the MOBILE block sets `flex-direction: row` and `text-align: left` back, and `.header-controls` to `justify-content: flex-end`, so it is the desktop arrangement — mark hard left, controls hard right. That only fits *because* the wordmark and the page label are gone, so the three rules are one decision. Measured 74px tall at 390px wide, on both a `home` route and in a room. The landing page's floating cassette (`.gartic-logo-top`) goes at the same time, under 820px: it is a second copy of the mark sitting ~90px under the header's, which reads as decoration on a wide box and as a duplicate on a phone. `display: none` rather than `visibility: hidden` — it is absolutely positioned, so hiding it would leave the space reserved — and the box's 64px of top padding, which exists *only* to clear that logo, drops to the 20px the sides use. ~96px of fold back at 390px.
  - Three long-standing collisions were found by measuring rather than looking, and **all three reproduce at 1440px** — they were phone-visible, not phone-caused: `.monitor-osd` overlapping `.player-display` on a voting console, and `.player-display-text` / `.tape-title` being flex-shrunk to 12px while holding 16px of text, so `overflow: hidden` cropped the glyphs through the middle and read as a strikethrough. Fixes are in globals.css with the measurements in the comments. The lesson generalises: on a console pinned to a fixed `height` with `!important`, any text row that can grow will crop a sibling.
- Server-side sanitize all user input at the handler: words stripped of whitespace and capped at 30 chars, chat at 300, `wordsPerPlayer` clamped 1–10, `imposterCount` clamped, reactions checked against a closed allowlist and throttled per player. Keep this up for new events.
- Env: `.env.example` is the template; `.env` and `.env.local` exist locally and are gitignored. `DATABASE_URL` points at SQLite (`file:./dev.db`); switching to Postgres also means editing `provider` in `prisma/schema.prisma`.
- YouTube access stays on the official IFrame API — no scraping or downloading (spec §5, ToS).

## Deployment note

Vercel cannot host this — serverless functions don't hold persistent websockets. Target Railway/Render running the custom Node server. In-memory rooms also mean this can't scale past one instance without moving room state to a shared store.
